# Build it on shadcn Base UI, scan-first, sapphire-sparing

Use shadcn/ui on its Base UI primitives rather than hand-building: the four components a collection app cannot do without (multi-select tag Combobox, swipeable bottom Drawer, Select, DropdownMenu) are exactly where hand-built Tailwind costs weeks of keyboard and screen-reader work, and in October 2026 shadcn ships all of them on Base UI with no `forwardRef`, no cmdk, no Vaul and a documented Vite + Tailwind 4 + React Router path; the realistic cost is **5–8 developer-days versus 3–5 weeks** for twenty accessible components. The UI itself should follow what the best-rated collector apps (Letterboxd, Collectr, PopGrinder, Delicious Library) converge on and what the worst-rated (the official Funko app at **2.0–2.8 stars**, hobbyDB) get wrong: an image-first grid of 3:4 tiles (2 columns at 390 px, 5–6 at 1440 px), a fixed four-button action row on every detail page, a "pick the destination once, then keep scanning" add flow that increments quantity instead of duplicating, filters as a bottom sheet on phone and an inline bar on desktop with applied-filter chips in both, and toast-with-Undo for every safe write. The shell is a 4-tab bottom bar with a single "Add" FAB below Tailwind's `lg` (1024 px) and a collapsible 256 px sidebar above it. On the palette, electric sapphire 500 `#004cff` is a legitimate primary (**6.04:1 with white text**, AA), ultrasonic 500 `#3e2ad5` is the best focus-ring and accent colour in the set (8.41:1), icy blue 50/100 and 900/950 carry the light and dark surfaces, and two ramps (baby blue ice, blue energy) should be demoted to chart colours because their 500 steps fail AA under white text (4.13:1 and 4.67:1 with no margin). In dark mode the 500 must never carry text or a fill: it drops to **3.09:1 on icy-950**, so the dark primary is sapphire 300 `#6694ff` with sapphire 950 text (6.75:1). Camera, barcode and PWA features all require HTTPS on the LAN (Caddy `tls internal`), the `barcode-detector` ponyfill must be used everywhere because Safari's native detector is still off and broken through iOS 26, and the photo input must omit `capture` so iOS offers Take Photo / Library and transcodes HEIC to JPEG.

## shadcn on Base UI wins by a factor of four on time, at a known configuration cost

The decision is not "component library versus Tailwind": shadcn copies source into the repo, so the output is Tailwind components you own either way. The question is whether the keyboard, focus and ARIA behaviour of about twenty primitives is written by you or by MUI's full-time Base UI team. Base UI became shadcn's default on July 3 2026 ("New projects now use Base UI by default. Radix is still fully supported… You do not need to migrate") and it is the only base with a native Combobox, Number Field and Drawer, which removes the cmdk and Vaul dependencies the Radix flavour needed ([shadcn changelog, July 2026](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default); [shadcndeck: Radix vs Base UI](https://www.shadcndeck.com/blog/radix-vs-base-ui)). Base UI 1.9.0 shipped on October 9 2026 on a monthly cadence, its components "adhere to the WAI-ARIA Authoring Practices", manage focus automatically with `initialFocus`/`finalFocus`, and support arrow keys, typeahead, Home/End and Escape ([Base UI releases](https://base-ui.com/react/overview/releases); [Base UI accessibility](https://base-ui.com/react/overview/accessibility)). shadcn removed `forwardRef` from every component in February 2025, so the generated files are plain functions compatible with React 19's `ref`-as-prop, and a 40-plus-component app under React Compiler 1.0 reported no shadcn breakage and a 142→144 KB bundle delta ([shadcn Tailwind v4 notes](https://ui.shadcn.com/docs/tailwind-v4); [eastondev](https://eastondev.com/blog/en/posts/dev/20260331-react-compiler-shadcn/)).

The honest counter-case is a native-element build: `<dialog>.showModal()` gives top layer, inert background, Escape and focus restore for free, and the W3C APA group agreed it needs no extra focus trap ([CSS-Tricks](https://css-tricks.com/there-is-no-need-to-trap-focus-on-a-dialog-element/)). That covers Modal, ConfirmDialog and Lightbox credibly. It covers nothing else: there is no native element for a multi-select combobox with chips, a bottom sheet with swipe-to-dismiss and `modal="trap-focus"`, a positioned dropdown menu with submenus, or a tooltip, and those are where audit findings land. One practitioner timed an accessible login form at **8 minutes with shadcn versus about 45 from scratch** ([whoffagents, April 2026](https://dev.to/whoffagents/shadcn-ui-in-2026-why-i-stopped-installing-component-libraries-and-started-owning-my-components-2eel)); scaled to this component list, the research note's own estimate is 15–25 days hand-built against 5–8 days with shadcn, with the data table and gallery costing the same either way. The alternatives do not change the verdict: Base UI used directly is "shadcn without the skin" (same primitives, you retype the class strings), Headless UI v2 is Tailwind-native but its ~10 components lack Drawer, Tooltip and a chip combobox, React Aria is the pick only if i18n or formal conformance evidence is a hard requirement, and daisyUI styles without behaving, which fails the team's accessibility rule outright ([greatfrontend headless roundup](https://www.greatfrontend.com/blog/top-headless-ui-libraries-for-react-in-2026); [daisyUI v5](https://daisyui.com/docs/v5/)).

The cost is a half-day of reconciliation with the team conventions, every item of which is known. The Vite guide still tells you to add `"baseUrl": "."`, which TypeScript 6 deprecates; skip it and write `paths` relative to the config, mirrored in Vite `resolve.alias` ([shadcn Vite install](https://ui.shadcn.com/docs/installation/vite)). Since September 2026 generated components import `cn` from the `cn` npm package rather than from the utils alias, so make `@utils/classNameUtils` a one-line re-export of it and run `migrate cn` to drop `clsx` and `tailwind-merge` ([shadcn changelog, September 2026](https://ui.shadcn.com/docs/changelog/2026-09-cn)). The entry CSS gains `@import "shadcn/tailwind.css"` from node_modules; if the "one CSS file" rule is read strictly, `shadcn eject` inlines it irreversibly ([shadcn CLI](https://ui.shadcn.com/docs/cli)). The base layer applies `* { border-border outline-ring/50 }`, which recolours every border in the app, so decide at init that `--border` is the icy-200 hairline ([shadcn manual install](https://ui.shadcn.com/docs/installation/manual)). `buttonVariants` co-exported from `button.tsx` trips `react-refresh/only-export-components`; move variant objects to sibling `buttonVariants.ts` files. Files under `src/common/components/ui/` are kebab-case with multiple named exports; treat that folder as vendored code (an explicit, documented exception to PascalCase-equals-default-export), and wrap the primitives in team-named components (`IconButton`, `ConfirmDialog`, `EmptyState`, `StatTile`) that do follow the rules. `style`, `tailwind.baseColor` and `cssVariables` are frozen after init ([components.json](https://ui.shadcn.com/docs/components-json)). Finally, react-hook-form is still silently broken under the React Compiler (`watch`, `isDirty`, `useFieldArray` go stale; RHF v8 was still beta mid-2026); the fix is a `useFormCompat` hook in `@hooks` whose first statement is `'use no memo'`, used in place of `useForm`, which is independent of shadcn and would be needed hand-built too ([hamzashabbir.dev](https://hamzashabbir.dev/article/react-compiler-react-hook-form-use-no-memo-fix); [react.dev incremental adoption](https://react.dev/learn/react-compiler/incremental-adoption)). shadcn's current form guidance uses `<Controller>` with the library-agnostic `<Field>` family, and `FieldError` takes any `{ message }` array, so `yupResolver` from `@hookform/resolvers/yup` plugs in with no shadcn-specific work; verify in the generated `field.tsx` that `aria-describedby` is wired, because the docs do not say ([shadcn Forms / React Hook Form](https://ui.shadcn.com/docs/forms/react-hook-form); [Field](https://ui.shadcn.com/docs/components/field)).

### Setup and component list

Run `yarn dlx shadcn@latest init` in the existing Vite app (or `init -t vite` for a fresh one), choose base `base`, base colour `neutral` (the palette below overrides every semantic token anyway), CSS variables on, and no `baseUrl`. In `components.json` set `aliases.components` to `@components`, `aliases.ui` to `@components/ui`, `aliases.hooks` to `@hooks`, `aliases.utils` and `aliases.lib` to `@utils`, each present in `tsconfig.app.json` `paths` and in `vite.config.ts` `resolve.alias`. Then `yarn dlx shadcn@latest add` the following, grouped by what they become in the app.

| Group | shadcn items (Base UI) | Becomes |
|---|---|---|
| Controls | `button`, `badge`, `toggle-group`, `tooltip`, `kbd` | Button, IconButton (size `icon` + `aria-label`), status chips, density and view toggles |
| Forms | `field`, `label`, `input`, `input-group`, `textarea`, `select`, `native-select`, `checkbox`, `switch`, `combobox` | FormField with RHF `Controller`; TagPicker = `combobox` with `multiple` chips; SortSelect = `select` |
| Overlays | `dialog`, `alert-dialog`, `drawer`, `sheet`, `popover`, `dropdown-menu` | Edit sheet, ConfirmDialog, phone filter bottom sheet (`drawer`, `swipeDirection="down"`), desktop filter popovers, row actions |
| Layout | `sidebar`, `tabs`, `card`, `separator`, `scroll-area`, `table`, `pagination` | Desktop shell, Owned/Wishlist tabs, StatTile base, item table |
| Feedback | `toast`, `skeleton`, `empty`, `spinner`, `progress` | Undo toasts, grid skeleton, empty states, upload rings |
| Optional | `carousel` (adds Embla), `chart` (adds Recharts) | Lightbox strip, stats charts |

Skip `sonner` (the July 2026 Base UI `toast` needs no extra dependency and supports actions, promises, stacking and swipe dismissal), skip `command` (cmdk is Radix-only; the Base UI `combobox` drives the ⌘K palette), and there is no `form` or `data-table` component to add: the table is a guide you compose yourself on `@tanstack/react-table` v9 ([Toast changelog](https://ui.shadcn.com/docs/changelog/2026-07-toast); [Data Table](https://ui.shadcn.com/docs/components/data-table)). Ban the `xs` and `icon-xs` sizes: at `h-6`/`size-6` they are exactly 24 px, WCAG 2.2's floor with zero margin ([button.json](https://ui.shadcn.com/r/styles/base-vega/button.json); [W3C 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). What stays hand-built, because no registry has it: PopCard and PopGrid (container queries), BottomNav and the Add FAB, Scanner and Viewfinder, PhotoUploader with its queue, Lightbox behaviour, StatTile, FilterChips row, ThemeToggle and PageHeader.

## Shell: 4-tab bar plus one FAB below 1024 px, sidebar above

Material's width classes and Apple's size classes agree on the mechanics: one pane with a bottom navigation bar on compact widths, a rail or sidebar once space allows, and the same functionality everywhere ("You can change how much functionality is visible, such as switching from a tab bar to a sidebar when there's more space") ([Android window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes); [Apple HIG Layout](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/layout.json)). For an app whose two real targets are 390 px and 1440 px, the simplest defensible rule is **bottom bar below Tailwind's `lg` (1024 px), persistent sidebar at and above it**; the 640–1023 band keeps the bar with a 3-column grid, which Material lists as acceptable for medium widths ([M3 window size classes](https://m3.material.io/foundations/layout/applying-layout/window-size-classes)). Drive the shell with viewport breakpoints and everything inside the content pane (grid columns, table-versus-cards) with container queries (`@container` on `<main>`, `@md:grid-cols-3 @3xl:grid-cols-4 @5xl:grid-cols-6`), because the content width depends on whether the sidebar is open, not on the viewport ([Tailwind responsive design](https://tailwindcss.com/docs/responsive-design)).

The bar carries four destinations: **Collection, Wishlist, Stats, Search**, Search last because Apple allows "a dedicated search tab at the trailing end", Settings behind a gear in the page header rather than a fifth tab. Labels are always on, single words, filled icons, and the bar never hides on scroll: "Use a tab bar to support navigation, not to provide actions" and "Make sure the tab bar is visible when people navigate to different sections" ([Apple HIG Tab bars](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/tab-bars.json)). That first rule is why "Add" is not a tab. It is a FAB, bottom-right above the bar, rendered only on the Collection and Wishlist screens, because Material restricts the FAB to "the most important action on a screen", one per screen, and omits it where the content items are themselves the primary action (so none on Stats) ([M3 FAB](https://m3.material.io/components/floating-action-button/guidelines)). Dimensions: 64 px of controls (Material's current Expressive height, down from 80) plus `pb-[env(safe-area-inset-bottom)]`, which on a home-indicator iPhone adds about 34 px; budget ~98 px of fixed bottom chrome and give the scroll container matching bottom padding so the last grid row and any sticky Save bar are never covered, which is WCAG 2.2's focus-not-obscured criterion in practice ([Material Components BottomNavigation](https://github.com/material-components/material-components-android/blob/master/docs/components/BottomNavigation.md); [WebKit: designing for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)). `env()` only returns non-zero with `viewport-fit=cover` in the viewport meta, and insets differ between Safari and the installed home-screen app, so test both ([WeWeb community](https://community.weweb.io/t/pwa-safe-area-using-env-safe-area-inset-bottom/17206); [WebKit bug 236445](https://bugs.webkit.org/show_bug.cgi?id=236445)).

On desktop the sidebar is 256 px expanded (Material's drawer caps at 280 dp), collapsible to a 64 px icon rail but not hidden by default (Apple: "Avoid hiding the sidebar by default"), with the primary **Add** button at its top where Material places the FAB on expanded windows, the four destinations beneath, and Settings plus the theme toggle in the footer ([Material NavigationDrawer](https://github.com/material-components/material-components-android/blob/master/docs/components/NavigationDrawer.md); [Apple HIG Sidebars](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/sidebars.json)). Cap the content column at `max-w-7xl` (80 rem/1280 px) so 1440 px does not stretch table rows to 1300 px, and keep prose and spec blocks at `max-w-prose` for Material's 40–60 character line ([Tailwind theme variables](https://tailwindcss.com/docs/theme)). Phone gutters are 16 px, desktop 24 px.

## Grid, detail and add flows copy Letterboxd and Collectr, not the Funko app

### Browsing

Letterboxd's "most recognizable design pattern is the poster grid… pages that feel like walking through a gallery", Collectr's grids are two-column with art, name, set, price and an add button, and Libib's most repeated review request is cover images in the list view, which settles the default: an image-first grid with a list alternative that always shows the thumbnail ([Blake Crosley on Letterboxd](https://blakecrosley.com/guides/design/letterboxd); [screensdesign Collectr](https://screensdesign.com/apps/collectr-tcg-collector-app/); [Libib reviews](https://apps.apple.com/app/id721908216)). Every tile is `aspect-[3/4]` with `object-cover` (a Funko box is roughly that ratio; `object-contain` on the surface colour only on the detail page where nothing may be cropped) and explicit `width`/`height` so there is no layout shift and the browser does not fetch every image at once ([web.dev responsive images](https://web.dev/learn/design/responsive-images); [web.dev lazy loading](https://web.dev/articles/browser-level-image-lazy-loading)). Column math with 12 px gaps: 2 columns at 390 px gives 175 px tiles, 3 at 640, 4 at 1024 with the sidebar open, 5–6 inside the 1280 px cap at 1440; keep tiles in the 160–220 px band, since above ~240 px a Funko photo is mostly background. Card anatomy under the photo: name in `text-sm font-medium line-clamp-2`, then `#number · series` in `text-xs` muted, with at most two small badges on the photo corner (Chase, Exclusive, or a quantity pill "×2"; PopGrinder shows up to four stickers per item and lets you choose one card per Pop or one per copy) ([PopGrinder](https://apps.apple.com/app/id6446220901)). The card itself is the link; do not nest buttons inside it ([Salt Card usage](https://www.saltdesignsystem.com/salt/components/card/usage)). Offer a two-step density toggle (comfortable/compact) in the header rather than pinch, which is a native gesture; Notion's card-size dropdown and Google Photos' three layouts are the precedents ([Notion galleries](https://www.notion.com/help/galleries); [TestingCatalog](https://www.testingcatalog.com/how-to-change-grid-layout-on-google-photos-for-android.md)).

Serve thumbnails from a fixed ladder of 200, 400, 800, 1200, 1600 and 2000 px widths; a 175 px CSS slot on a 3× phone wants the 600-ish candidate, a 400 px detail column on a 2× display wants 800, the lightbox 1600–2000 ([web.dev responsive images article](https://web.dev/articles/responsive-images)). Each thumbnail carries a ≤10 px blur placeholder, never a spinner ([Next.js Image docs](https://nextjs.org/docs/app/api-reference/components/image)). For 500 items do not infinite-scroll: NN/g finds endless scrolling "not recommended for goal-oriented finding tasks" and that people remember "it was on page 3"; use a page size of 60 (divisible by 2, 3, 4, 5 and 6 columns) with an "N–M of 500" label, or "Load more" with the same counter if one long page on phone is preferred, and restore scroll position when returning from a detail page, the bug Immich users hit ([NN/g infinite scrolling](https://www.nngroup.com/articles/infinite-scrolling/); [NN/g tips](https://www.nngroup.com/articles/infinite-scrolling-tips/); [Immich #9417](https://github.com/immich-app/immich/issues/9417)). The list view becomes a real `<table>` from `@3xl` of container width with a sticky header, a sticky name column if it overflows, and a right-edge fade as the overflow cue; below that it collapses to rows showing photo, name, number and status with the rest behind a disclosure ([NN/g mobile tables](https://www.nngroup.com/articles/mobile-tables/)). Sort must be stable, locale-aware and use the Pop number as the visible secondary key, because "it'll sort A-Z, but the titles within each letter are completely random" is a top Discogs complaint, and every count on screen must come from the same query as the list, because PopGrinder's home-screen count disagreeing with the inner total is a one-star review ([worldsapps Discogs reviews](https://worldsapps.com/reviews-discogs); [PopGrinder](https://apps.apple.com/app/id6446220901)).

### Detail

Letterboxd repeats one fixed row of four equal action buttons under the poster on every item view; Collectr adds a price chart with tabs, "View Sold Listings" and a "Report incorrect photo" flow; the Funko app earns "crashes the app when clicking on items" and prices "stuck at 'insufficient data'", and hobbyDB "tapping some menu options opens separate windows" ([screensdesign Letterboxd](https://screensdesign.com/apps/letterboxd/); [screensdesign Collectr](https://screensdesign.com/apps/collectr-tcg-collector-app/); [SplitMetrics Funko](https://splitmetrics.com/apps/funko/id1286964746); [hobbyDB reviews](https://apps.apple.com/us/app/hobbydb-vision/id1537173276)). So the detail page is: hero photo with a 48–64 px thumbnail strip (desktop) or a dot/count indicator (phone), tapping into a lightbox; a fixed action row of **Owned (toggle, exposing a quantity stepper when on), Wishlist, Edit, More**; a two-column spec block (number, line, series, type, chase/exclusive flags, barcode); a user block (quantity, condition, paid price, purchase date, location tag, tags, notes) whose Edit opens a pre-filled sheet, not a separate page; and an explicit "Search on eBay" link, a link and not part of any card tap. Fields with no data are hidden or say "No price yet — add one", never a dead label. On `lg` the page is two panes, photo column left and facts right. The lightbox encodes PhotoSwipe's defaults, which are the de facto spec: swipe between photos, swipe-down and Escape to close, pinch and double-tap zoom, arrow keys, `trapFocus` and `returnFocus`, preload one before and two after, and intrinsic width/height supplied for every image ([PhotoSwipe options](https://photoswipe.com/options/)). Under `prefers-reduced-motion` the zoom-in opening becomes a fade, per Apple's guidance to replace scaling transitions ([Apple HIG Accessibility](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/accessibility.json)).

### Adding

The pattern has not changed since Delicious Library in 2004: "If you select a shelf on the left sidebar, then scan a barcode, the book is automatically added to the selected shelf", and a blogger used one virtual shelf per physical box so he could "browse shelf by shelf or box by box" ([Home Theater Forum](https://www.hometheaterforum.com/community/threads/anyone-use-delicious-library-to-catalog-dvds.196037/); [Fazal Majid](https://blog.majid.info/organizing-with-delicious-library/)). Collectr modernises it as viewfinder → result card with your photo beside the match → one "Add" with editable condition; Libib added "a 'continue scanning' option when an item isn't found"; the failure modes collectors punish are scanners that "lag, freeze, or crash" after one or two scans (hobbyDB), scans that dump you into full manual entry (Libib, Sortly), and re-adding a copy that "tends to create duplicate entries" (Sortly, PopGrinder) ([screensdesign Collectr](https://screensdesign.com/apps/collectr-tcg-collector-app/); [Libib](https://apps.apple.com/app/id721908216); [hobbyDB reviews](https://apps.apple.com/us/app/hobbydb-vision/id1537173276); [Zoftware Hub Sortly](https://zoftwarehub.com/products/sortly/reviews)).

The resulting flow, as one route `/add` with three steps on phone and one two-column page on desktop: the FAB opens the scanner directly, with a sticky header "Adding to: Owned · Box 3" whose destination and location tag are chosen once and remembered. A hit shows a bottom card: suggested name from the barcode lookup, the barcode pre-filled, editable number and series (the earlier API research established that Pop number and line are not in any legitimately accessible machine-readable source and must stay user-editable fields that lookups merely suggest), a quantity stepper and **Add**; Add fires a toast "Added · Undo" and returns to the live viewfinder so the next box can be scanned without a tap. A scan of a barcode already in the collection offers **"+1 quantity"** and "Add as separate entry", never a silent duplicate. Not-found shows "Type it in (barcode kept)" and "Keep scanning". Photo capture is a button on that confirm card (one tap to attach a shelf photo) rather than a separate edit step. Step 3, details, is a single-column form even at 1440 px (`max-w-xl`), labels above fields, the few optional fields marked "(optional)", validation on blur and then per keystroke once a field is in error, and a sticky bottom Save bar with `pb-[env(safe-area-inset-bottom)]` so the keyboard never hides it ([NN/g form usability](https://www.nngroup.com/articles/web-form-design/); [Baymard inline validation](https://baymard.com/blog/inline-form-validation)). On desktop the camera is rarely the input; the barcode field also accepts a USB keyboard-wedge scanner, and the photo area is a drop zone in the left column. First run is a single empty state on Collection: "No Pops yet" with "Scan a barcode" and "Import spreadsheet" (PopArchive's import path is the realistic start for an existing collector), and camera permission is requested only when Scan is tapped, never stacked up front the way Letterboxd's three back-to-back prompts are ([AlternativeTo PopArchive](https://alternativeto.net/software/poparchive/about/); [screensdesign Letterboxd](https://screensdesign.com/apps/letterboxd/); [NN/g empty states](https://www.nngroup.com/articles/empty-state-interface-design/)).

## Scanner and uploads must route around Safari, not through it

Safari's native `BarcodeDetector` is "Disabled by default" on macOS 17.0–27.1 and iOS 17.0–27.2, the flag-enabled path has been broken since iOS 18 with WebKit bug 281848 still open at its last comment on 2026-07-21, and desktop Chrome supports it only on macOS and ChromeOS ([caniuse BarcodeDetector](https://caniuse.com/mdn-api_barcodedetector); [WebKit bug 281848](https://bugs.webkit.org/show_bug.cgi?id=281848); [MDN BCD #9030](https://github.com/mdn/browser-compat-data/issues/9030)). Mere existence of `window.BarcodeDetector` therefore proves nothing. Ship the `barcode-detector` ponyfill (zxing-wasm underneath, ~1.04 MiB for the reader build) on every platform, import from `barcode-detector/ponyfill` rather than the polyfill (which does not check whether an existing global actually works), restrict formats to `ean_13`, `upc_a`, `upc_e`, `ean_8`, and self-host the `.wasm` from `public/wasm/` via `prepareZXingModule({ overrides: { locateFile } })` so a LAN-only app has no jsDelivr dependency; lazy-load the scanner route so the wasm stays off the critical path ([barcode-detector README](https://github.com/Sec-ant/barcode-detector); [zxing-wasm README](https://github.com/Sec-ant/zxing-wasm)). UPC-A is EAN-13 with a leading zero; normalise to GTIN-13 server-side, and remember from the earlier research that every Funko UPC observed starts with the GS1 prefix 889698, a cheap "is this a Funko" check before the UPCitemdb lookup.

Camera: `getUserMedia({ audio: false, video: { facingMode: { ideal: "environment" }, width: { ideal: 1280 }, height: { ideal: 720 } } })`, started from a tap, into `<video autoplay muted playsinline>`. Do not request `focusMode` or `zoom` (Android Chrome only), show a torch button only when `track.getCapabilities().torch === true` and keep your own boolean because iOS 18 misreported `getSettings().torch` ([Dynamsoft focus](https://www.dynamsoft.com/codepool/camera-focus-control-on-web.html); [WebKit bug 280970](https://bugs.webkit.org/show_bug.cgi?id=280970)). Drive detection from `requestVideoFrameCallback` (Safari 15.4+) throttled to one `detect()` every 100–200 ms, crop a centred region of about 80 % width by 30 % height into an `OffscreenCanvas` for 1D codes, and accept a read only when two consecutive frames agree ([caniuse rVFC](https://caniuse.com/wf-request-video-frame-callback)). Scandit's usability rules shape the viewfinder: dim outside the region, "do not over-restrict the area, as user will feel like they're scanning through a keyhole", draw an overlay on the detected code, give sound/haptic/visual feedback, and put the camera in standby between scans; Strich adds that a manual-entry fallback "is therefore always recommended" ([Scandit usability](https://docs.scandit.com/data-capture-sdk/web/best-practices-for-usability.html); [Strich best practices](https://docs.strich.io/best-practices-for-scanning-apps.html)). `navigator.vibrate` is a no-op on iOS, so success is a flash plus a short sound. Stop all tracks on route unmount and restart on `visibilitychange`, because iOS freezes background streams; home-screen (standalone) PWAs carry a long tail of still-open WebKit camera bugs, so test the scanner installed and, if it misbehaves, tell the user to scan from Safari ([WebKit bug 273938](https://bugs.webkit.org/show_bug.cgi?id=273938); [WebKit bug 282327](https://bugs.webkit.org/show_bug.cgi?id=282327)). On `NotAllowedError` show OS-specific recovery text (iOS: Settings › Apps › Safari › Camera, or the "aA" menu › Website Settings).

None of this works on `http://192.168.x.x`: `navigator.mediaDevices`, service workers and wasm threads all need a secure context, and iOS has no insecure-origin override. The lowest-friction fix for one Linux Docker host, one iPhone and one Mac is Caddy's `tls internal`, which issues from a local CA whose root lives at `/data/caddy/pki/authorities/local/root.crt` and lasts ~10 years while leaves rotate every 12 hours; export it, AirDrop to the iPhone, install the profile, then Settings › General › About › Certificate Trust Settings, because Apple states a manually installed certificate "isn't automatically trusted for SSL" ([Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https); [Caddy tls directive](https://caddyserver.com/docs/caddyfile/directives/tls); [Apple HT102390](https://support.apple.com/en-ca/102390)). Use a `.home.arpa` name, not `.local` (mDNS on Apple devices). The upgrade path if other devices ever join is a real domain with Caddy's Cloudflare DNS-01 plugin, which needs no root on any device ([Helge Klein](https://helgeklein.com/blog/automatic-https-certificates-for-services-on-internal-home-network-without-opening-firewall-port/)). The PWA itself is modest: `display: "standalone"`, `id`, `scope`, a 192 and a 512 px icon plus a 512 px `"purpose": "maskable"` icon with ~20 % padding, `viewport-fit=cover`, and two `<meta name="theme-color" media="(prefers-color-scheme: …)">` tags because "the manifest itself can't express light and dark preferences" ([web.dev web app manifest](https://web.dev/learn/pwa/web-app-manifest)). iOS has no install prompt, so show a one-time "Share › Add to Home Screen" hint when `display-mode: standalone` does not match; the installed app also gets its own ITP storage counter, though field reports contradict Apple on that, so keep the upload queue in IndexedDB as a cache and never as the only copy ([Search Engine Land on ITP](https://searchengineland.com/what-safaris-7-day-cap-on-script-writeable-storage-means-for-pwa-developers-332519); [WebKit bug 232302](https://bugs.webkit.org/show_bug.cgi?id=232302)).

Photo upload is governed by three WebKit behaviours. First, a plain `<input type="file" accept="…">` without `capture` is what gives iOS the Take Photo / Photo Library / Choose File menu, while `capture` sends the user straight to the camera; combining `capture` with `multiple` yields one photo per picker session and `input.files` is replaced each time, confirmed by Apple DTS on iOS 26.4, so a dedicated "Take photo" button needs a second single-file input and a `File[]` you accumulate yourself across `change` events ([W3C webrtc list, youennf](https://lists.w3.org/Archives/Public/public-webrtc-logs/2020Sep/0092.html); [Apple Developer Forums 826732](https://developer.apple.com/forums/thread/826732)). Second, Safari transcodes HEIC "to the first item in the list" of `accept`, and listing `image/*` first prevents that conversion, so the input is `accept="image/jpeg,image/png,image/webp" multiple`, with server-side HEIC handling kept as a backstop because the picker's "Current" option can still deliver it ([WebKit bug 292350](https://bugs.webkit.org/show_bug.cgi?id=292350); [WebKit bug 273444](https://bugs.webkit.org/show_bug.cgi?id=273444)). Third, iOS caps a canvas at ~16.7 megapixels and a 48 MP iPhone frame is 48.8 MP, so decode and downscale in one step with `createImageBitmap(file, { imageOrientation: "from-image", resizeQuality: "high", resizeWidth })` to a 2048 px long edge, draw into an `OffscreenCanvas`, `convertToBlob` as JPEG at ~0.82, set the canvas to 1×1 afterwards to release memory, and process files one at a time ([pqina canvas area](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/); [WebKit bug 231063](https://bugs.webkit.org/show_bug.cgi?id=231063)). The UI is Immich's: a thumbnail grid from object URLs, a circular progress ring per tile driven by axios `onUploadProgress`, a per-file retry, a global "3 of 5 uploaded" line, concurrency capped at 2–3 ([Linuxiac on Immich 1.99](https://linuxiac.com/immich-1-99-0-brings-upload-indicators-optimizations-and-more/)). Because Safari suspends JavaScript about three seconds after backgrounding and `visibilitychange` is not reliably fired, persist the queue to IndexedDB before each upload starts, give every photo a client UUID so retries are idempotent, retry on `online` with 1-2-4-30 s backoff, and show "keep this screen open" for large batches ([Frontend Masters background JS](https://frontendmasters.com/courses/background-javascript/observing-mobile-background-javascript); [WebKit bug 207256](https://bugs.webkit.org/show_bug.cgi?id=207256)). A successful upload gets a toast with Undo that deletes the asset.

## Filters as chips, undo as the default confirmation

Filtering removes items and sorting reorders what is left; keep them as two controls even when they share a surface, and keep the applied state visible after the sheet closes "through chips, a summary, or a badge" ([screensdesign filter & sort patterns](https://screensdesign.com/articles/mobile-app-filter-sort-ui-examples/)). Baymard found 28 % of benchmarked sites show no applied-filters overview and that a bare count "performed poorly"; the fix is a horizontally scrolling chip row above the results, an "x" on each chip, "Clear all", the filter type on ambiguous values, and "Filter (3)" on the trigger as a supplement ([Baymard applied filters](https://baymard.com/research-articles/how-to-design-applied-filters)). On phone, then: a search field at the top, beside it a `Sort: Name A–Z` select and a "Filters (n)" chip that opens a Base UI `drawer` from the bottom at no more than 50 % height, expandable, with the live result count on its commit button ("Show 128 results", eBay's pattern) ([M3 bottom sheets](https://m3.material.io/components/bottom-sheets/guidelines); [eBay filtering patterns](https://playbook.ebay.com/design-system/patterns/filtering-patterns)). Because the dataset is 500 local rows, filters apply immediately (Cancel just closes), which the pattern guidance explicitly allows for content libraries where "combinations are cheap"; Baymard's objection to autosubmit concerns slow, paged e-commerce results. On desktop the same facets become an inline row of popovers above the grid, the same chip row underneath, and "128 results" next to the sort select. Facets for this app: status (owned/wishlist), line/series, type (Pop, Rides, Deluxe), flags (chase, exclusive, vaulted, glow, flocked), location tag, tags, condition, price range. Search is a ⌘K palette on desktop whose empty state shows recent items and three to five verbs (Add, Scan, Go to Stats), results grouped Items / Series / Actions with shortcuts shown on the right, and a full-screen Search tab on phone with the keyboard open on entry and a camera icon beside the field for "find by scanning", Discogs's placement ([Maggie Appleton on command bars](https://maggieappleton.com/command-bar); [Discogs iOS search](https://support.discogs.com/hc/en-us/articles/360014043894-How-To-Search-In-The-Database-When-Using-The-Discogs-iOS-App)).

Feedback follows one policy. Every safe write (add, edit, delete one item, move to a list) returns a past-tense toast with a single literal "Undo" for 6–8 s; Material's snackbar guidance caps it at one action, bottom placement above the FAB and bar, never stacked, and warns that on web an auto-dismissing message must also appear inline if it matters, while Vercel's Geist specifies 5–10 s for Undo toasts "only when rollback is safe" ([M3 snackbar](https://m3.material.io/components/snackbar/guidelines); [Vercel Geist toast](https://vercel.com/geist/toast)). Validation and server errors never go in a toast: they are an inline alert above the form buttons plus field-level messages bound with `aria-describedby` and `aria-invalid`, as Carbon prescribes for in-flow notifications ([Carbon notifications](https://carbondesignsystem.com/components/notification/usage/)). A confirm dialog (`alert-dialog`) is reserved for multi-item deletes and anything not undoable. Loading: route loaders deliver data before render on a LAN, so show nothing under a second, a layout-mirroring skeleton only for a slow first paint of the grid, a spinner for a single module, and a progress bar for anything over ten seconds such as an import; never a "no items" message while loading ([NN/g skeleton screens](https://www.nngroup.com/articles/skeleton-screens/)). Four empty states are needed and must look unlike the skeleton: first-use collection, no results after filters ("Clear filters" button), empty wishlist, empty search. Stats stays glanceable: KPI tiles of label, a `text-3xl tabular-nums` value with unit, and one comparison line, two per row on phone and four on desktop; quantities as bars and lines, never gauges or donuts, since "People don't perceive colors as ordered" and about 4.5 % of people have a colour-vision deficiency ([NN/g dashboards](https://www.nngroup.com/articles/dashboards-preattentive/)). Useful tiles, taken from what Collectr, PopGrinder and PopArchive ship: owned, wishlist, chase and exclusive counts, total and average paid, spend over time with 1M/6M/1Y/All tabs, breakdown by line, series completion, recent additions, five most expensive; skip "current value" charts entirely because the API research found no legitimate price source and stale values are the Funko app's loudest complaint.

## Sapphire for the 10 %, icy for the 90 %, 500 never in the dark

The 60-30-10 rule is the frame: the dominant 60 % is a near-neutral background, 30 % is surfaces and type, and the 10 % accent is "vibrant and high-contrast, used sparingly" for buttons and calls to action ([Cieden 60-30-10](https://cieden.com/book/sub-atomic/color/60-30-10-rule)). In a single-hue palette the trap is that blue headings, blue icons, blue borders and blue buttons leave nothing reading as the one clickable thing; Apple's version is "avoid applying a similar color to tab labels and content layer backgrounds" ([Apple HIG Tab bars](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/tab-bars.json)). So saturated sapphire is reserved for primary buttons, links, selected states and the FAB; everything else is icy blue at its palest and darkest steps, which behave as blue-tinted greys, the Radix "slate" idea of a neutral scale whose hue matches the accent ([Radix composing a palette](https://www.radix-ui.com/colors/docs/palette-composition/composing-a-palette)). Ratios below were computed from the exact ramp hexes with the WCAG 2.x relative-luminance formula; AA is 4.5:1 for normal text, 3:1 for large text and for UI component boundaries such as input borders and focus rings.

The ramp audit first. With white text, **electric sapphire 500 `#004cff` reaches 6.04:1, 600 `#003dcc` 8.27:1, ultrasonic 500 `#3e2ad5` 8.41:1 and 400 `#6555dd` 5.39:1**, all AA. Baby blue ice 500 `#0077ff` reaches only 4.13:1 (fails), blue energy 500 `#046bfb` 4.67:1 (passes with no margin), icy blue 500 `#1991e6` 3.37:1 (fails) and icy 600 `#1474b8` 4.98:1. Sapphire 400 `#3370ff` fails with white (4.28) and only just passes with sapphire-950 text (4.57), so it is not a light-mode fill. Two consequences: baby blue ice and blue energy carry no UI role and become `--chart-1..5` series colours alongside icy 500 and ultrasonic 400, and icy 500 appears in the light theme for exactly one job, input borders, where its **3.37:1 on white and 3.01:1 on icy-50** clear the 3:1 boundary rule that icy 400 (2.63) cannot.

Three things in that table are deliberate. The light text colour is sapphire-950 rather than icy-950 so body text and the primary share a hue family; either passes everywhere. The dark primary is the 300 step with dark text on it, which is Material's rule that dark-theme primaries live in the 200–300 tones because "saturated colors can vibrate against dark backgrounds and cause eye strain", and it is also arithmetic: **sapphire 500 on icy-950 is 3.09:1**, enough for a 3:1 decorative stroke, not for a label or a filled button, so the 500 never carries text in dark mode ([Material dark theme](https://m2.material.io/design/color/dark-theme.html)). The dark primary-hover goes lighter (200), not darker, for the same reason. And the status colours are absent from the palette on purpose; a monochrome brand still needs error, success and warning, borrowed from outside the ramps (Radix pairs blue with red/ruby, green/jade and amber), used only on chips, dots and inline alerts that also carry a text label, never as large fills, and checked for the same ratios before use ([Radix composing a palette](https://www.radix-ui.com/colors/docs/palette-composition/composing-a-palette)).

Dark mode has a few more rules than a token swap. Elevation is expressed by lighter surfaces, not bigger shadows: icy-950 background, icy-900 cards, icy-800 for hover rows, sheets and menus, each layer separated by a 1 px hairline (`--border`) because icy-950 to icy-900 is only a 1.08 step and would otherwise vanish; shadows stay on floating layers only and never become glows ([Material Components dark theme](https://github.com/material-components/material-components-android/blob/master/docs/theming/Dark.md)). Text is icy-50, not pure white, following web.dev's "rgb(250, 250, 250) works well". Product photos on white box backgrounds glare on a navy surface, so apply `brightness(0.9)` and a `ring-1 ring-white/10` to grid tiles in dark mode and render blur placeholders on the surface colour, not white ([web.dev prefers-color-scheme](https://web.dev/articles/prefers-color-scheme)). Set `color-scheme: light dark` so native controls and scrollbars follow, animate only `color` and `background-color` for ~200 ms on toggle, and use shadcn's three-way `ThemeProvider` (light / dark / system, persisted in localStorage) with an inline `<head>` script so the first paint is already the right theme ([shadcn dark mode for Vite](https://ui.shadcn.com/docs/dark-mode/vite); [Tailwind dark mode](https://tailwindcss.com/docs/dark-mode)).

The Tailwind 4 wiring keeps the five ramps as ordinary `@theme` colours (so `bg-electric-sapphire-500` utilities exist for charts and one-offs), puts the runtime-switchable semantic values in `:root` and `.dark`, and bridges them with `@theme inline`, which is the mechanism shadcn already uses and the only way a `var()` chain resolves where the variable is redefined ([Tailwind theme variables](https://tailwindcss.com/docs/theme); [shadcn theming](https://ui.shadcn.com/docs/theming)):

```css
@import "tailwindcss";
@import "shadcn/tailwind.css"; /* or run `shadcn eject` and inline it */
@custom-variant dark (&:is(.dark *));

@theme {
  --color-icy-blue-50: #e8f4fc;  /* … all five ramps, 50–950, exact hexes … */
  --color-electric-sapphire-500: #004cff;
  --color-ultrasonic-blue-500: #3e2ad5;
  --radius: 0.625rem;
  --ease-standard: cubic-bezier(0.2, 0, 0, 1);
  --ease-decelerate: cubic-bezier(0.05, 0.7, 0.1, 1);
}

:root {
  --background: var(--color-icy-blue-50);
  --foreground: var(--color-electric-sapphire-950);
  --card: #ffffff;                --card-foreground: var(--foreground);
  --popover: #ffffff;             --popover-foreground: var(--foreground);
  --muted: var(--color-icy-blue-100);   --muted-foreground: var(--color-icy-blue-700);
  --primary: var(--color-electric-sapphire-500); --primary-foreground: #ffffff;
  --accent: var(--color-ultrasonic-blue-500);    --accent-foreground: #ffffff;
  --border: var(--color-icy-blue-200);
  --input: var(--color-icy-blue-500);
  --ring: var(--color-ultrasonic-blue-500);
  color-scheme: light;
}
.dark {
  --background: var(--color-icy-blue-950);
  --foreground: var(--color-icy-blue-50);
  --card: var(--color-icy-blue-900);     --card-foreground: var(--foreground);
  --popover: var(--color-icy-blue-800);  --popover-foreground: var(--foreground);
  --muted: var(--color-icy-blue-800);    --muted-foreground: var(--color-icy-blue-300);

  --border: var(--color-icy-blue-800);
  --input: var(--color-icy-blue-500);
```

shadcn's own `@theme inline { --color-background: var(--background); … }` block then stays untouched, and `bg-background text-foreground border-border focus-visible:ring-ring` work in both modes without `dark:` prefixes. Hex is fine inside `@theme`; OKLCH is shadcn's convention, not a requirement. Focus rings are `focus-visible:ring-2 focus-visible:ring-ring ring-offset-2`, which at 7.5–8.4:1 light and 3.5–5.6:1 dark is visible on every surface in the table. The rest of the token set needs no invention: Tailwind's default type scale (card title `text-sm font-medium`, caption `text-xs`, page title `text-2xl` on phone and `text-3xl` on `lg`, KPI `text-3xl tabular-nums`), the system font stack with InterVariable as the upgrade only if table numerals misalign, three radii (6 / 10 / 16 px via `--radius`), 44 px touch targets with `pointer-coarse:` and 40 px pointer targets, and Material's motion tokens (150 ms for colour and press, 200–250 ms for chips, menus and toasts, 300 ms in / 200 ms out for sheets and dialogs, standard easing `cubic-bezier(0.2, 0, 0, 1)`), with every positional animation under `motion-safe:` and reduced to a ≤150 ms fade under `motion-reduce:` ([Tailwind font-size](https://tailwindcss.com/docs/font-size); [rsms.me/inter](https://rsms.me/inter/); [Material 3 MotionTokens](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/MotionTokens.kt); [web.dev prefers-reduced-motion](https://web.dev/articles/prefers-reduced-motion)).

## Conclusion

The research reframes the two headline questions. "shadcn or hand-built" turns out to be a question about four components, not twenty: a chip-based tag combobox, a swipeable bottom sheet, a select and a dropdown menu are the only places where the libraries earn their keep, and Base UI's July 2026 promotion to shadcn's default made those four native, dependency-light and Compiler-safe at the same moment. Everything specific to a Funko collection (the 3:4 tile grid, the scanner viewfinder, the upload queue, the stat tiles, the bottom bar and FAB) is hand-built regardless, and it is where the design effort should go. Similarly, "one blue palette, light and dark" turns out to be a numbers problem with a clean answer once the exact ramps are measured: sapphire 500 is a textbook light primary and a textbook dark-mode mistake, two of the five ramps have no UI job, and icy blue at its extremes is a better neutral than any grey because it keeps the whole interface in one hue without spending saturation.

The strategic consequence is that the hard parts of this app are not in the UI layer at all. They are the Safari platform edges (a broken native barcode detector, camera streams that freeze in installed PWAs, HEIC transcoding governed by the order of an `accept` list, JavaScript suspended three seconds after backgrounding) and the absence of any sanctioned catalog, which forces Pop number and series to remain user-owned fields. Design the add flow and the data model around those constraints first, and the shadcn components and the token table above become a day of configuration rather than a design project.
